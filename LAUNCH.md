# Launching Historify

Everything in this document is something only you can do, because it involves
accounts, money and legal identity. The code is already written: the database
schema, the auth system, Stripe Checkout, the webhook and the subscription
gates all exist and are wired together. What is missing is a running database,
a running API, and the credentials that connect them.

Nothing here asks you to paste a secret into a chat. Every value goes straight
into a provider's own dashboard.

---

## What exists already

| Piece | State |
|---|---|
| User accounts, password hashing, sessions | Built (`server/src/routes/auth.ts`) |
| Database schema | Built (`server/prisma/schema.prisma`) |
| Stripe Checkout, billing portal, webhook | Built (`server/src/routes/billing.ts`) |
| Subscription gates in the app | Built |
| Frontend already calls Stripe when an API is configured | Built (`src/pages/PricingPage.tsx`) |
| A running database | **You create this** |
| A running API server | **You create this** |
| Stripe account and prices | **You create this** |

The app currently runs entirely in the browser. Accounts live in each visitor's
own browser storage, which is why your testers cannot see each other and why
nobody can pay you yet. Steps 1-4 change that.

## Step 1 - Deploy the database and API

The repository has a Render blueprint (`render.yaml`) that creates both.

1. Sign up at render.com and connect your GitHub account.
2. **New > Blueprint**, pick this repository, branch
   `claude/historify-learning-app-r54nl`.
3. Render reads `render.yaml` and proposes a Postgres database plus a web
   service. Accept.
4. It will ask you for the values marked `sync: false`. For now, set only:

   - `CORS_ORIGIN` = `https://historify2026.netlify.app`
   - `FRONTEND_URL` = `https://historify2026.netlify.app`

   Leave the Stripe ones blank until Step 3.

`JWT_SECRET` and `CSRF_SECRET` are generated by Render. You will never see
them and you do not need to. They are different values on purpose, so rotating
one does not force the other.

The server refuses to boot on a weak or missing secret rather than starting up
insecure, so if the first deploy fails, read the log - it names the exact
variable and what is wrong with it.

When it is up, `https://<your-service>.onrender.com/healthz` returns OK.

> **Note on the free plan:** Render's free tier sleeps after inactivity, so the
> first request after a quiet period takes ~30 seconds. Fine for testing,
> not for paying customers. The paid tier removes it.

---

## Step 2 - Point the app at the API

In **Netlify > Site configuration > Environment variables**, add:

- `VITE_API_URL` = `https://<your-service>.onrender.com`

Redeploy. This single variable is what flips the app from browser-only storage
to real accounts: registration, login, friends, the leaderboard and payments
all start going to your server.

## Step 3 - Stripe

### 3a. Create the account

Go to stripe.com and register. Stripe will ask for your legal details - this
is the part that makes the money legally yours, and it is not optional:

- Your legal name and address, or your company's if you register one
- A bank account in the same name, for payouts
- Your tax identification number
- Proof of identity

**Decide first whether you are trading as yourself or as a company.** As an
individual you are personally liable and the income is your personal income.
A registered company separates that. This is a real decision with tax
consequences in your country and it is worth an hour with an accountant before
you click anything. I can't advise on which is right for you.

### 3b. Create three products

In the Stripe dashboard, **Products > Add product**. Create one per plan, each
with a **recurring monthly** price in USD:

| Product | Price | Must match |
|---|---|---|
| Beginner Student | $4.99 / month | `src/features/subscription/plans.ts` |
| Pro Student | $9.99 / month | same |
| Master Student | $16.99 / month | same |

Copy each price's ID - it looks like `price_1ABCxyz...`, not the product ID.

> **These numbers are not linked to the app's code.** The app displays the
> price from `plans.ts`; Stripe charges whatever the Price object says. If you
> change one and not the other, customers see one number and get billed
> another. Whenever you change a price, change it in both places.

### 3c. Put the keys into Render

Back in Render, on the `historify-api` service, **Environment**:

- `STRIPE_SECRET_KEY` - from Stripe **Developers > API keys**. Use the
  **test** key (`sk_test_...`) until you have made a test purchase end to end.
- `STRIPE_PRICE_BEGINNER`, `STRIPE_PRICE_PRO`, `STRIPE_PRICE_MASTER` - the
  three price IDs from 3b.

Never put the secret key into Netlify or anywhere in this repository. It
belongs only on the server. The app never sees it.

### 3d. The webhook

This is the step people skip, and skipping it means customers pay and never get
upgraded - Stripe takes the money, your database never hears about it.

1. Stripe **Developers > Webhooks > Add endpoint**
2. URL: `https://<your-service>.onrender.com/api/billing/webhook`
3. Events: `checkout.session.completed`, `customer.subscription.updated`,
   `customer.subscription.deleted`, `invoice.payment_failed`
4. Copy the signing secret (`whsec_...`) into Render as
   `STRIPE_WEBHOOK_SECRET`.

The server verifies every webhook's signature and rejects anything older than
five minutes, so a leaked URL alone cannot forge an upgrade.

### 3e. Test before going live

With test keys, buy each plan using Stripe's test card `4242 4242 4242 4242`,
any future expiry, any CVC. Check that:

- Checkout completes and returns you to the app
- The account's tier actually changes
- The gated features unlock
- Cancelling through the billing portal downgrades the account

Only then swap the test keys for live keys (`sk_live_...`) and create a second
webhook endpoint for live mode. **Live and test mode have separate keys,
separate prices and separate webhooks.** Copying a test price ID into a live
deployment is the single most common way this breaks.

## Step 4 - The legal minimum

You are about to hold other people's personal data and charge them money.
Several of your testers are in the EU, so GDPR applies regardless of where you
are.

**You need, before taking real payments:**

- **A privacy policy** saying what you collect (email, username, learning
  progress), why, how long you keep it, and who you share it with (Stripe,
  your hosting provider, Anthropic for the AI features).
- **Terms of service** covering what people are buying, your refund policy and
  cancellation terms.
- **A way to delete an account.** GDPR gives people the right to erasure, and
  the app has no delete-account flow yet. This is a genuine gap - tell me and
  I will build it.
- **A cookie/consent notice** if you add analytics later. You do not need one
  for the session cookie alone, which is strictly necessary.
- **Stripe handles PCI compliance for you** as long as card details are only
  ever entered on Stripe's own hosted Checkout page, which is what this app
  does. Do not build your own card form; it would put you in a completely
  different compliance bracket.

I can draft the privacy policy and terms, but have someone qualified read them
before you publish. I am not able to give you legal advice.

---

## What I would do in what order

1. Steps 1 and 2. Get real accounts working with no money involved, and let
   your testers use them. This is the part most likely to surface bugs.
2. Step 4's privacy policy and account deletion, while testing continues.
3. Step 3 in test mode. Prove the whole purchase path works.
4. Swap to live keys.

Do not skip 3's test mode. Taking a real payment you cannot fulfil is a much
worse problem than a delayed launch.
